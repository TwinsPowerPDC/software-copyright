# 项目材料完整性检查清单

本清单用于阶段二：分析并识别材料缺口，对照用户提供的材料评估完整性，确定哪些信息已知、哪些需推断、哪些需向用户补充询问。

---

## 一、材料读取顺序

读取用户提供的项目材料时，按以下层次深入各端代码：

**后端（Java/Node.js）**：Service 层 → Repository/DAO 层 → Controller 层 → 实体类

**前端（React/Vue）**：页面入口 → 核心组件 → API 调用层 → 工具函数

**微信小程序**：app.json → 核心页面 → 自定义组件

> 大型项目不必读取每个文件，优先读取各层代表性文件（各1-2个），重点关注函数签名、类名、接口路径、注释说明。

---

## 二、材料优先级清单

| 优先级 | 材料类型 | 用途 | 缺失时的处理策略 |
|--------|----------|------|----------------|
| 🔴 必须 | 源代码文件（核心模块） | 生成代码文档、理解功能实现、识别技术栈 | 无法进行，必须要求用户提供路径 |
| 🔴 必须 | 功能说明/PRD/README | 理解业务功能，生成设计文档背景章节 | 从代码注释和命名推断，标注为推断值 |
| 🟠 重要 | package.json / pom.xml | 确认技术栈版本 | 从代码 import 语句推断版本范围 |
| 🟠 重要 | 数据库表结构说明 | 生成核心业务对象定义（字段、类型、约束） | 从实体类/Model 文件推断，可能缺少字段注释 |
| 🟡 有助 | 接口文档（Swagger/Postman） | 生成接口说明章节（路径、参数、响应） | 从 Controller 注解提取，手动整理 |
| 🟡 有助 | 架构设计图/文字描述 | 生成技术架构章节 | 从技术栈和代码结构推断架构 |
| 🟡 有助 | 项目已有草稿 | 了解哪些内容已写，避免重复，续写未完成章节 | 无草稿则全新生成 |
| ⚪ 可选 | 运行截图/UI原型 | 补充功能描述的细节 | 无则从代码逻辑描述功能 |
| ⚪ 可选 | 测试报告/UAT记录 | 补充系统稳定性描述 | 不影响核心材料生成 |

## 三、材料盘点输出模板

在阶段二结束时，输出以下格式的盘点结果：

```
📋 材料盘点结果

✅ 已获取：
  - 功能模块（从PRD/README识别）：[列举识别到的模块名称]
  - 技术栈（从 package.json/pom.xml 确认）：[列举技术栈和版本]
  - 核心数据对象（从实体类识别）：[列举主要实体类名称]
  - 核心接口（从 Controller 识别）：[X 个Controller，约 Y 个接口]

⚠️ 需确认（AI 已推断，请核实）：
  - [推断项1]：[推断内容] — 推断依据：[说明]
  - [推断项2]：[推断内容] — 推断依据：[说明]

❌ 缺失（将影响以下章节）：
  - [缺失材料]：影响[设计文档第X章/源代码文档的XX部分]
  - 处理方案：[AI将如何处理这个缺口]

📝 补充问题（如需要，最多3个）：
  1. [问题1]
  2. [问题2]
  3. [问题3]
```

## 四、按设计文档章节的材料需求

### 第一章 需求背景
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| 系统建设背景 | README、PRD | 从项目名称和功能模块推断行业背景 |
| 目标用户群体 | PRD、README | 从菜单/角色设计推断用户类型 |
| 核心痛点 | PRD | 从功能模块名称推断解决的问题 |
| 系统规模预期 | PRD | 从系统定位推断 |

### 第二章 核心业务对象
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| 数据库字段名称 | 实体类/DDL/README | 直接从实体类字段提取 |
| 字段业务含义 | 代码注释/接口文档 | 从字段名称和使用场景推断 |
| 字段约束规则 | 校验注解/数据库约束 | 从 @NotNull、@Size、数据库 DDL 提取 |
| 枚举值含义 | 枚举类/常量类/注释 | 从枚举名称和使用方式推断 |

### 第三章 功能模块设计
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| 模块划分 | 菜单配置/路由配置/PRD | 从前端路由或菜单表推断模块结构 |
| 搜索/筛选条件 | 前端组件/Controller 参数 | 从查询 DTO 字段推断搜索条件 |
| 表单字段 | 前端组件/DTO | 从 Form 组件或请求 DTO 提取 |
| 业务流程逻辑 | Service 实现类/代码注释 | 直接从业务代码流程分析 |
| 操作权限控制 | 注解/权限配置 | 从 @PreAuthorize 等注解推断 |

### 第四章 技术架构
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| 框架版本 | package.json、pom.xml | 从依赖声明直接读取 |
| 架构模式 | 目录结构、代码结构 | 从 controller/service/dao 分层推断 |
| 部署方式 | Dockerfile、nginx.conf | 从配置文件推断；无则写常见方案 |
| 数据库类型 | application.yml、pom.xml | 从数据库驱动依赖推断 |

### 第五章 接口说明
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| 接口路径 | Controller 注解 | 直接从 @RequestMapping 读取 |
| 请求方法 | Controller 注解 | 直接从 @GetMapping 等注解读取 |
| 请求参数 | DTO 类/方法参数 | 从方法签名和 DTO 字段提取 |
| 响应结构 | 返回类型/VO 类 | 从方法返回类型和 VO 类字段提取 |

### 第六章 运行环境
| 需要的信息 | 材料来源 | 推断策略 |
|-----------|---------|---------|
| JDK 版本 | pom.xml、Dockerfile | 从 `<java.version>` 或基础镜像推断 |
| 数据库版本 | docker-compose.yml、README | 从镜像版本或 README 说明推断 |
| 服务器配置 | README、部署文档 | 填写通用建议值（4核8G以上） |
| 浏览器要求 | README、前端代码 | 根据前端框架版本推断兼容性 |
| 小程序版本 | app.json、project.config.json | 从 miniprogramRoot 配置推断 |

## 五、技术栈识别快速指南

### Java 后端识别
| 文件 | 关键字段 | 识别内容 |
|------|---------|---------|
| pom.xml | `<spring-boot.version>` | Spring Boot 版本 |
| pom.xml | `<java.version>` | Java 版本 |
| pom.xml | `mybatis-plus-boot-starter` | ORM 框架 |
| pom.xml | `mysql-connector-java` | 数据库类型 |
| pom.xml | `spring-boot-starter-data-redis` | 缓存方案 |
| application.yml | `spring.datasource.url` | 数据库版本 |

### Node.js 后端识别
| 文件 | 关键字段 | 识别内容 |
|------|---------|---------|
| package.json | `"express"` 或 `"koa"` | Web 框架 |
| package.json | `"sequelize"` 或 `"prisma"` | ORM 框架 |
| package.json | `"engines.node"` | Node.js 版本要求 |

### 前端识别
| 文件 | 关键字段 | 识别内容 |
|------|---------|---------|
| package.json | `"react"` 版本 | React 框架版本 |
| package.json | `"vue"` 版本 | Vue 框架版本 |
| package.json | `"antd"` | UI 组件库 |
| package.json | `"typescript"` | 是否使用 TypeScript |
| tsconfig.json | 存在 | 使用 TypeScript |

### 微信小程序识别
| 文件 | 关键字段 | 识别内容 |
|------|---------|---------|
| project.config.json | `"miniprogramRoot"` | 小程序根目录 |
| app.json | `"pages"` | 页面列表 |
| project.config.json | `"libVersion"` | 基础库版本 |

## 六、推断质量评级与确认策略

AI 在**材料盘点阶段（对话中）**对不同确定性的信息采取不同处理策略：

| 确定性等级 | 含义 | 对话中的处理 | 最终文档中的呈现 |
|-----------|------|------------|----------------|
| 高确定性 | 直接从材料中读取 | 盘点时列为"✅ 已获取" | 直接写入文档，无需标注 |
| 中确定性 | 基于代码逻辑或命名推断 | 盘点时列为"⚠️ 需确认"，**在对话中请用户核实** | 用户确认后写入文档，不带任何标注 |
| 低确定性 | 参考行业惯例填写 | 盘点时列为"⚠️ 需确认"，**在对话中请用户核实或修改** | 用户确认后写入文档，不带任何标注 |
| 无法推断 | 需用户提供 | 盘点时列为"❌ 缺失"，**必须在对话中向用户收集** | 用户提供后写入文档，不带任何标注 |

**⚠️ 铁律：`（推断值，请核实）`、`（建议值，可修改）`、`⚠️ 待补充` 等标注仅用于对话过程中与用户沟通，严禁出现在最终生成的三份交付文档中。所有不确定信息必须在文档生成前完成确认。**

## 七、向用户提问的原则

**单次提问上限**：最多3个问题，避免问卷式体验

**提问优先级**（按影响程度排序）：

1. 申请表日期信息（公司成立日期、开发完成日期、发表日期）
2. 著作权人（公司全称）和联系信息
3. 软件名称和简称

**提问格式参考**：

```
在开始生成材料之前，需要确认几个申请表必填信息：

1. 软件全称是什么？（格式：XX系统 V1.0）
2. 著作权人是谁？（公司全称，如"XX科技有限公司"）
3. 关键日期：
   - 公司成立日期（YYYYMMDD）：_____
   - 开发完成日期（YYYYMMDD）：_____
   - 首次发表日期（YYYYMMDD）：_____

   ⚠️ 提醒：三个日期必须满足：成立日期 < 完成日期 < 发表日期
```
